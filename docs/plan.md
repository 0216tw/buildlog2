# BuildLog 개발 계획

## 1. 문서 목적

이 문서는 `PRD.md`와 `spec.md`에 정한 BuildLog 첫 버전을 FastAPI, React, SQLite 3로 개발하는 순서를 설명합니다.

현재 개발 데이터는 프로젝트 내부의 SQLite 3에 저장하고, 자동 테스트는 별도의 임시 SQLite 데이터베이스를 사용합니다.

각 Phase는 기능 구현, 실패 처리, 권한 확인, 테스트를 모두 마친 뒤 다음 Phase로 넘어갑니다.

## 2. 확정한 기술 구성

| 영역 | 기술 | 역할 |
| --- | --- | --- |
| 프론트엔드 | React, TypeScript, Vite | 사용자가 보는 화면과 입력 처리 |
| 백엔드 | Python, FastAPI | 회원, 기록, 검색, 댓글, 좋아요, 신고 API |
| 데이터 처리 | SQLAlchemy, Alembic | SQLite 데이터 구조와 변경 이력 관리 |
| 현재 개발 DB | SQLite 3 | 로컬 사용자와 기록 데이터 저장 |
| 테스트 DB | 임시 SQLite 3 | 자동 테스트마다 독립적인 데이터 저장 및 초기화 |
| 백엔드 테스트 | pytest | API, 입력 조건, 권한, 데이터 동작 확인 |
| 프론트엔드 테스트 | Vitest, React Testing Library | 화면 입력과 사용자 동작 확인 |

### 중요한 경계

- 회원가입과 로그인 기능은 FastAPI가 처리합니다.
- React는 FastAPI API만 호출합니다.
- React에서 SQLite에 직접 연결하지 않습니다.
- SQLite 파일 위치와 앱 비밀 키는 백엔드 환경 설정에서 관리합니다.
- 자동 테스트는 개발 데이터를 건드리지 않고 임시 SQLite를 사용합니다.
- Supabase 연결은 관련 수업을 진행한 뒤 별도 작업으로 정합니다.

## 3. 권장 폴더 구조

```text
buildlog/
├─ backend/
│  ├─ app/
│  │  ├─ api/          # FastAPI 주소와 요청 처리
│  │  ├─ core/         # 환경 변수, 인증, 공통 설정
│  │  ├─ db/           # 데이터베이스 연결과 공통 설정
│  │  ├─ models/       # 데이터 저장 구조
│  │  ├─ schemas/      # API 입력·출력 형식
│  │  ├─ services/     # 기능 규칙과 권한 처리
│  │  └─ main.py       # FastAPI 시작점
│  ├─ alembic/         # 데이터베이스 변경 이력
│  ├─ tests/           # SQLite를 사용하는 백엔드 테스트
│  ├─ .venv/           # Python 가상환경, Git 제외
│  ├─ .env             # 실제 비밀 설정, Git 제외
│  └─ .env.example     # 비밀값이 없는 설정 항목 예시
├─ frontend/
│  ├─ src/
│  │  ├─ api/          # FastAPI 호출 코드
│  │  ├─ components/   # 공통 화면 조각
│  │  ├─ pages/        # 페이지 단위 화면
│  │  ├─ routes/       # 화면 이동과 로그인 제한
│  │  └─ main.tsx      # React 시작점
│  ├─ .env             # 로컬 화면 설정, Git 제외
│  └─ .env.example     # 공개 가능한 설정 항목 예시
├─ database/
│  ├─ README.md        # 로컬 데이터베이스 사용 안내
│  └─ buildlog.sqlite3 # 개발 중 만드는 로컬 DB, Git 제외
└─ docs/
```

실제 구현 중 파일을 더 나눌 수 있지만 기능 범위는 바꾸지 않습니다.

## 4. 환경별 데이터베이스 사용법

| 환경 | 데이터베이스 | 원칙 |
| --- | --- | --- |
| 자동 테스트 | 임시 SQLite 3 | 각 테스트가 독립적으로 실행되고 개발 데이터를 사용하지 않음 |
| 로컬 개발 | SQLite 3 | `database/buildlog.sqlite3`에 데이터를 저장함 |
| 현재 첫 버전 | SQLite 3 | FastAPI만 데이터베이스에 접근함 |

Supabase 연결과 검증은 현재 Phase 범위에서 제외하고 관련 수업 이후 별도로 계획합니다.

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준과 환경 확인

#### 목표

코드와 패키지를 만들기 전에 개발 도구, 데이터 연결 방식, 비밀 설정 항목을 확정합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위와 기술 구성이 일치하는지 확인합니다.
2. Python, Node.js, npm 실행 여부와 버전을 확인합니다.
3. 서로 호환되는 안정 버전의 FastAPI, React, Vite, SQLAlchemy를 선택합니다.
4. Python 가상환경 위치를 `backend/.venv`로 확정합니다.
5. 프론트엔드 개발 주소를 `http://localhost:5173`으로 정합니다.
6. 백엔드 개발 주소를 `http://127.0.0.1:8000`으로 정합니다.
7. API 기본 주소를 `/api`로 정합니다.
8. 백엔드 환경 변수 이름을 정합니다.
   - `DATABASE_URL`: FastAPI 실행용 로컬 SQLite 접속 문자열
   - `TEST_DATABASE_URL`: SQLite 테스트 접속 문자열
   - `APP_SECRET_KEY`: 로그인 정보 보호에 사용할 비밀 키
   - `FRONTEND_ORIGIN`: 허용할 React 화면 주소
9. 프론트엔드 환경 변수 이름을 정합니다.
   - `VITE_API_BASE_URL`: FastAPI 기본 주소
10. `.env.example`에는 항목 이름과 안전한 예시만 두고 실제 비밀값을 적지 않습니다.
11. Supabase 연결은 관련 수업 뒤 별도 작업으로 정함을 확인합니다.
12. 서버 실행, 프론트 실행, 테스트 명령을 기록할 `docs/setup.md`의 구성을 정합니다.

#### 변경 파일

- `docs/mvp.md`
- `docs/PRD.md`
- `docs/spec.md`
- `docs/plan.md`
- `docs/setup.md`
- 이 Phase에서는 애플리케이션 코드와 패키지를 변경하지 않음

#### 확인 방법

- 세 문서에서 이전 기술 구성의 전제가 남아 있지 않은지 확인합니다.
- 로컬 개발 DB와 임시 테스트 DB의 역할이 구분되어 있는지 확인합니다.
- 비밀값을 사용자에게 채팅으로 요구하거나 문서에 기록하지 않는지 확인합니다.
- 개발 도구가 설치되어 있는지 읽기 전용 명령으로 확인합니다.

#### 완료 조건

- 기술 구성과 환경 변수 목록이 확정되어야 합니다.
- Phase 1을 시작할 때 사용자가 추가로 선택해야 할 기술 항목이 없어야 합니다.

### Phase 1. FastAPI 백엔드 뼈대 만들기

#### 목표

데이터 기능 없이 FastAPI 서버와 백엔드 테스트를 실행할 수 있게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 만듭니다.
2. FastAPI, 실행 서버, 설정 관리, SQLAlchemy, Alembic, 테스트 패키지를 설치합니다.
3. 정확한 패키지 버전을 백엔드 의존성 파일에 기록합니다.
4. `backend/app/main.py`와 공통 폴더를 만듭니다.
5. 환경 변수를 읽는 설정을 만듭니다.
6. `GET /api/health` 상태 확인 API를 만듭니다.
7. React 개발 주소만 허용하도록 CORS 기본 설정을 만듭니다.
8. SQLite를 사용하는 첫 API 테스트를 작성합니다.
9. `.gitignore`에 백엔드 가상환경, `.env`, SQLite 파일, 캐시를 확인·보완합니다.
10. 이 Phase에서는 사용자나 기록 테이블을 만들지 않습니다.

#### 완료 조건

- FastAPI 서버와 API 문서가 열립니다.
- 상태 확인 API와 SQLite 테스트가 통과합니다.
- 외부 데이터베이스 접속 정보 없이 기본 테스트를 실행할 수 있습니다.

React 화면을 실행하고 FastAPI API와 통신할 수 있게 합니다.

#### 작업

2. 페이지, 공통 컴포넌트, API 호출, 화면 이동 폴더를 만듭니다.
3. `VITE_API_BASE_URL`을 읽는 설정을 만듭니다.
4. FastAPI 상태 확인 API를 호출하는 임시 화면을 만듭니다.
5. 연결 성공, 연결 실패, 불러오는 중 상태를 구분해 보여줍니다.
6. 기본 화면 이동 구조와 로그인 필요 화면 보호 틀을 준비합니다.
7. 첫 프론트엔드 테스트를 작성합니다.
8. `.gitignore`에 `node_modules`, `dist`, 프론트엔드 `.env`가 제외되는지 확인합니다.

#### 완료 조건

- React 개발 서버가 실행됩니다.
- React에서 FastAPI 상태 확인 결과를 볼 수 있습니다.
- 프론트엔드 테스트와 빌드가 통과합니다.
- React 코드에 데이터베이스 접속 정보가 없습니다.

### Phase 3. SQLite 데이터베이스 구조

#### 목표

로컬 개발과 자동 테스트에서 사용할 SQLite 데이터 구조를 만듭니다.

#### 작업

1. SQLAlchemy 로컬 DB 연결과 임시 테스트 DB 연결을 분리합니다.
2. Alembic 데이터베이스 변경 이력을 준비합니다.
3. 사용자, 공부 기록, 할 일, 오류 기록 모델을 만듭니다.
4. 댓글, 좋아요, 신고 모델을 만듭니다.
5. 기본 공개·완료·해결 상태와 중복 방지 규칙을 적용합니다.
6. SQLite에서 테이블 생성과 모델 테스트를 실행합니다.
7. 첫 Alembic 변경 이력을 빈 SQLite 데이터베이스에 적용하고 되돌립니다.
8. 모델과 Alembic 변경 이력이 같은 구조인지 확인합니다.

#### 완료 조건

- SQLite 모델 테스트와 Alembic 적용·되돌리기가 모두 통과합니다.
- 개발용 SQLite 파일과 임시 테스트 파일이 Git에 포함되지 않습니다.

### Phase 4. 회원가입·로그인·닉네임 변경

#### 목표

FastAPI 인증 API와 React 회원 화면을 연결합니다.

#### 작업

1. 회원가입, 로그인, 현재 사용자 확인, 닉네임 변경 API를 만듭니다.
2. 이메일, 비밀번호 8~64자, 닉네임 2~20자와 중복 규칙을 적용합니다.
3. 비밀번호를 안전하게 저장하고 로그인 상태를 안전하게 유지합니다.
4. 일반 사용자와 운영자 권한을 구분합니다.
5. React 회원가입, 로그인, 내 기록 홈, 계정 설정 화면을 만듭니다.
6. 성공 후 이동과 실패 시 입력값 유지 규칙을 적용합니다.
7. 로그인하지 않은 사용자의 기록 API와 화면 접근을 막습니다.

#### 완료 조건

- 사용자 A, 사용자 B, 운영자 계정을 구분할 수 있습니다.
- 회원 기능의 정상·실패·권한 테스트가 SQLite에서 통과합니다.

2. 해결 방법은 비어 있거나 1~5,000자가 되게 합니다.
3. 새 오류를 미해결·비공개로 저장합니다.
4. 해결 상태에는 해결 방법이 반드시 있도록 검사합니다.
5. 전체·미해결·해결 필터와 최신순 목록을 만듭니다.
6. 오류 제목과 오류 내용으로 내 기록을 검색합니다.
7. 해결 시각 저장과 해결 취소 시 시각 삭제를 적용합니다.
8. 해결 취소 후 해결 방법은 유지합니다.
9. 작성자만 해결·수정·삭제할 수 있게 합니다.
10. API와 React 테스트를 작성합니다.

#### 완료 조건

- 오류 기록 전체 흐름, 해결 규칙, 필터, 검색, 권한 테스트가 통과합니다.

---

### Phase 8. 공개 범위·공개 기록·공개 검색

#### 목표

로그인한 사용자가 다른 사용자의 공개 기록을 찾아 읽을 수 있게 합니다.

#### 작업

1. 작성자만 세 기록의 공개 여부를 바꾸게 합니다.
2. 공개된 세 기록을 한 API와 화면에서 최신순으로 제공합니다.
3. 기록 종류별 필터를 만듭니다.
4. 공부 기록은 제목·내용, 할 일은 제목, 오류는 제목·내용·해결 방법으로 검색합니다.
5. 공개 기록에 현재 작성자 닉네임을 보여줍니다.
6. 비공개 기록이 목록, 검색, 직접 API 요청으로 노출되지 않게 합니다.
7. 로그인하지 않은 사용자는 공개 기록도 볼 수 없게 합니다.
8. 다른 사용자의 공개 기록은 수정·삭제할 수 없게 합니다.

#### 완료 조건

- 공개 목록·필터·검색과 비공개 접근 차단 테스트가 통과합니다.

---

### Phase 9. 댓글 기능

#### 목표

공개 공부 기록과 오류 기록에서 댓글을 작성·수정·삭제할 수 있게 합니다.

#### 작업

1. 댓글 1~500자와 공백 처리 규칙을 적용합니다.
2. 댓글을 오래된 순서로 제공합니다.
3. 댓글 작성자는 자신의 댓글을 수정·삭제할 수 있게 합니다.
4. 기록 작성자는 자신의 기록에 달린 댓글을 삭제할 수 있게 합니다.
5. 공개 할 일에는 댓글 API와 화면을 제공하지 않습니다.
6. 기록이 비공개가 되면 댓글을 유지하되 숨기고, 다시 공개하면 보여줍니다.
7. 현재 작성자 닉네임을 댓글에 보여줍니다.
8. API 권한과 React 흐름 테스트를 작성합니다.

#### 완료 조건

- 댓글 입력, 순서, 권한, 공개 전환 테스트가 통과합니다.
- 댓글 답글 기능은 포함되지 않습니다.

---

### Phase 10. 좋아요 기능

#### 목표

공개 공부 기록과 오류 기록에서 좋아요를 등록·취소할 수 있게 합니다.

#### 작업

1. 사용자와 대상 기록 조합의 중복을 데이터베이스에서 막습니다.
2. 처음 누르면 등록하고 다시 누르면 취소하는 API를 만듭니다.
3. 현재 사용자의 좋아요 상태와 전체 개수를 제공합니다.
4. 공개 할 일에는 좋아요 API와 화면을 제공하지 않습니다.
5. 기록이 비공개가 되면 좋아요를 유지하되 숨기고, 다시 공개하면 보여줍니다.
6. 빠른 중복 요청과 실패 시 상태 유지 테스트를 작성합니다.

#### 완료 조건

- 좋아요 등록·취소·중복 방지·개수·공개 전환 테스트가 통과합니다.

---

### Phase 11. 신고와 운영자 확인

#### 목표

공개 기록과 댓글 신고를 접수하고 운영자만 확인할 수 있게 합니다.

#### 작업

1. 공개 세 기록과 댓글을 신고 대상으로 제한합니다.
2. 신고 이유 1~500자와 공백 규칙을 적용합니다.
3. 한 사용자가 같은 대상을 한 번만 신고하게 합니다.
4. 신고만으로 대상을 자동 삭제하거나 숨기지 않습니다.
5. 실패 시 신고 이유를 React 화면에 유지합니다.
6. 운영자 전용 신고 목록·상세 API와 React 화면을 만듭니다.
7. 일반 사용자의 운영자 API와 화면 접근을 막습니다.
8. 대상 기록이 비공개가 되어도 신고는 운영자가 볼 수 있게 합니다.
9. 신고 처리 상태, 자동 제재, 자동 삭제는 추가하지 않습니다.

#### 완료 조건

- 신고 입력, 중복 방지, 운영자 권한, 공개 전환 테스트가 통과합니다.

---

### Phase 12. 반응형 화면과 공통 실패 처리

#### 목표

모든 화면의 모양과 성공·실패 처리를 통일하고 휴대폰에서도 사용할 수 있게 합니다.

#### 작업

1. 밝은 배경과 카드형 목록을 공통 스타일로 정리합니다.
2. 메뉴, 버튼, 입력칸, 성공·실패 안내를 공통 컴포넌트로 정리합니다.
3. FastAPI 오류 응답을 React에서 같은 방식으로 보여줍니다.
4. 저장·수정 실패 시 입력값 유지 규칙을 모든 화면에서 확인합니다.
5. 권한 없는 버튼은 숨기되 FastAPI 권한 검사도 유지합니다.
6. 360px부터 큰 컴퓨터 화면까지 레이아웃을 확인합니다.
7. Chrome, Edge, Safari 최신 두 버전에서 주요 흐름을 확인합니다.
8. 범위 밖 기능을 암시하는 메뉴나 버튼을 제거합니다.

#### 완료 조건

- 화면 크기와 브라우저가 달라도 기능과 권한이 같습니다.
- 공통 실패 처리와 입력값 유지 규칙이 모든 기능에서 동작합니다.

---

### Phase 13. 전체 통합·SQLite 검증·실행 문서

#### 목표

SQLite 자동 테스트와 로컬 데이터 유지 동작을 함께 확인하고 MVP를 완료합니다.

#### 작업

1. 모든 백엔드 테스트를 SQLite로 실행합니다.
2. 모든 프론트엔드 테스트와 빌드를 실행합니다.
3. 사용자 A, 사용자 B, 운영자로 전체 권한 시나리오를 확인합니다.
4. 빈 SQLite 데이터베이스에 Alembic 변경 이력을 처음부터 적용합니다.
5. SQLite에서 회원, 세 기록, 공개 검색, 댓글, 좋아요, 신고 흐름을 확인합니다.
6. 서버를 다시 실행한 뒤 로컬 SQLite 데이터가 유지되는지 확인합니다.
7. 비공개 기록이 목록, 검색, 직접 API 요청에서 노출되지 않는지 다시 확인합니다.
8. `.env.example`에 실제 비밀값이 없는지 확인합니다.
9. 설치, 환경 변수, 실행, 테스트, DB 변경 방법을 `docs/setup.md`에 작성합니다.
10. `spec.md`의 모든 확인 항목을 실행합니다.
11. 실패한 항목만 수정하고 새 기능은 추가하지 않습니다.

#### 완료 조건

- SQLite 자동 테스트가 모두 통과합니다.
- React 테스트와 배포용 빌드가 통과합니다.
- 로컬 SQLite에서 MVP 전체 흐름과 데이터 유지가 동작합니다.
- 문서만 보고 새 환경에서 프로젝트를 실행할 수 있습니다.

## 8. Phase 진행 규칙

각 Phase는 아래 조건을 모두 만족해야 완료로 표시합니다.

- [ ] 해당 기능의 정상 흐름이 동작합니다.
- [ ] 입력값의 최소·최대와 실패 흐름을 확인했습니다.
- [ ] 로그인 여부와 작성자·운영자 권한을 확인했습니다.
- [ ] SQLite 자동 테스트가 통과했습니다.
- [ ] 해당 Phase에서 요구한 SQLite 마이그레이션 확인이 통과했습니다.
- [ ] React 화면과 FastAPI API의 결과가 일치합니다.
- [ ] 컴퓨터와 360px 화면에서 사용할 수 있습니다.
- [ ] `spec.md`와 다르게 구현된 부분이 없습니다.
- [ ] 새 기능을 임의로 추가하지 않았습니다.

진행 순서는 다음과 같습니다.

1. 한 번에 Phase 하나만 진행합니다.
2. Phase 결과와 테스트 결과를 공유합니다.
3. 다음 Phase가 요구하는 사용자 준비 사항이 있다면 시작 전에 알립니다.
4. 요구사항이 바뀌면 먼저 `PRD.md`, `spec.md`, `plan.md`를 함께 수정합니다.
